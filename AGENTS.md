# Portfolio repository instructions

## Scope

These instructions apply to this entire repository. This project is maintained
as a public showcase as well as a working codebase.

## Public-first standard

When changing the README, documentation, repository layout or public assets:

- Lead with the project's outcome and value in plain language.
- Treat non-technical visitors as the first README audience; preserve deeper
  technical material lower in the page or in linked documentation.
- Identify one primary public artifact. Place no more than two prominent links
  above the hero image or preview.
- Prefer one representative, current visual over several decorative images.
- Include a compact explanation of the problem, input, output and value.
- Describe three to five concrete capabilities the project demonstrates.
- Make important claims checkable through tests, examples, methodology, data
  provenance or explicit assumptions.
- State limitations and maturity honestly. Do not imply production readiness,
  accuracy, deployment health or test coverage without evidence.
- Put architecture and reproducibility after the public story. Put installation,
  API details, quality gates and the repository map later still.
- Keep secondary formats and deep documentation out of the primary call to
  action. Link to them in a later Deliverables or Documentation section.
- Keep the repository root focused; place internal procedures and long process
  documents under `docs/` or `.github/` where practical.
- Preserve the actual product, analysis, presentation, report and generated
  outputs unless the user explicitly requests changes to them.

## Required workflow

Before editing, inspect the existing README, repository metadata, file tree,
primary artifact and working-tree status. Reorder and simplify existing content
before adding new material.

Before publishing:

1. inspect the rendered README as a visitor would see it;
2. verify every primary link, image, file path and command;
3. confirm the description, homepage and topics match the README;
4. check that CI, demo and result claims are true;
5. review the first screen for a non-technical reader;
6. commit only intended files and push only when authorised.

If project-specific instructions conflict with these portfolio defaults, follow
the more specific instruction and preserve the user's explicit intent.
